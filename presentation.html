The aim

communication medium.

Every laser and LED is already a transmitter switching billions of times a second. We wanted to see what it takes to carry real files — text, images and audio — across one of them, end to end.

This is not a pure software project. Putting it on the air takes real hardware — a laser and a photodiode, and the boards to drive them.

The physical layer

Every payload comes down to on, or off.

A sentence, a compressed image, a second of audio — by the time any of it reaches the beam, it is only bits. The laser has two states, and the receiver reads them back one at a time.

  1. A 1 switches the laser on; a 0 switches it off.
  2. The photodiode turns each flash of light back into a small voltage.
  3. Above the threshold is a 1, below it a 0 — and the byte is whole again.
How it is built

Two problems. Solved separately.

Making bytes, and moving bytes. We keep them completely apart — which is exactly why one beam can carry three very different kinds of media.

Making bytes — Images

Transmit a representation,
not the pixels.

Sending a photograph pixel by pixel is impractical over an optical link of this kind. The Snapdragon X Elite NPU reduces the image to a compact latent representation of a few hundred bytes. Only that representation crosses the beam, and the Adreno 702 GPU on the Arduino UNO Q reconstructs it — both models running entirely on local Qualcomm silicon, with no cloud and no CPU fallback.

Making bytes — Audio

Audio doesn’t split cleanly.
So we split it where it’s safe.

Meta’s open-source EnCodec reduces a clip to two codebook streams and rebuilds it on the far side — again entirely on local Qualcomm silicon. But its decoder is recurrent: those layers carry state across the whole clip, and state cannot be fixed-shape or accelerated. So we cut the graph exactly where the state ends.

CPU — recurrent front

Codebooks and the stateful layers run over the complete clip so recurrent state is never broken. No acceleration here — that is the constraint, not a shortcut.

Accelerator — compute tail

Everything past the cut is pure fixed-shape compute with no memory of what came before. It runs strictly on the GPU/NPU, with CPU fallback disabled.

Moving bytes — Three channels

From one channel
to three.

The initial implementation used a single laser and a single photodiode, transmitting one byte at a time, to establish that the link was correct. We then distributed the same frame across three independent laser channels driven by a shared clock, reducing transfer time without altering the protocol.

Where we started — one channel
D5

One emitter, one detector. Bytes 0, 1, 2, 3… in order, nothing in flight beside them.

Where we are now — three channels
D5
D7
D9

Byte 0 on lane one, 1 on lane two, 2 on lane three — one shared clock, a third of the slots, the same CRC-checked frame.

Payload Bytes One channel Three channels
Image64 × 64 124 27.25 s 9.25 s
Image128 × 128 328 68.05 s 22.85 s
Image256 × 256 932 188.85 s 63.05 s
Audio24 kHz mono, two chunks 376 77.65 s 26.05 s

The output is byte-for-byte identical — same image, same audio, same quality. Only the time changes. And nothing in the protocol caps it at three; the channel count is a hardware budget, not a design limit.

Use cases

Everywhere radio can’t go.

End to end, every byte crosses the gap as light and nothing else — no Wi-Fi, no Bluetooth, no cellular, no network of any kind. The phone application does not even hold an internet permission.

The platform

Qualcomm silicon at every node.

Every stage of this pipeline is an AI workload, and each one executes on a Qualcomm NPU or GPU. Compression, reconstruction and display all run on-device, with no cloud inference and no network dependency at any stage.
